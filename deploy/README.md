# Сервер EV8 Ops — как поднять и как обслуживать

Дата: 28.09.2026. Устройство — как у Self Platform (`practices.md` §2, ТЗ v1.1
«тот же стек, чтобы не поддерживать два набора инструментов»): один сервер,
один Caddy на входе, два compose-проекта рядом.

```
        :80 :443
           │
       ┌───▼────┐  ev8-edge (свой compose-проект, свои сертификаты)
       │ Caddy  │
       └───┬────┘
           │ 127.0.0.1
     ┌─────┴──────┬──────────────┐
  :5173         :5174
┌────▼─────┐  ┌───▼──────┐        у каждого свои db · api · worker · web,
│ ev8-prod │  │ ev8-test │        свой том, своя база, свой .env
│  (тег)   │  │(develop) │
└──────────┘  └──────────┘
```

Наружу смотрит только Caddy. У стеков нет ни одного порта на публичном
интерфейсе: web слушает `127.0.0.1`, база и API — вообще ничего.

**Сервер:** `204.168.149.105`, Ubuntu 26.04, 2 ядра, 3.8 ГБ, 75 ГБ. Docker
установлен 28.09. **Вход по SSH — только по ключу** (с 13.10.2026, когда
репозиторий с этим адресом стал публичным): пароль сервер не принимает,
настройка лежит в `/etc/ssh/sshd_config.d/00-keys-only.conf`. Новому
компьютеру ключ добавляют через панель Hetzner или с машины, у которой
ключ уже есть.

## Чем серверный стек отличается от ноутбучного

`docker-compose.yml` — это ноутбук. `docker-compose.prod.yml` — **отдельный
файл**, а не набор переопределений, потому что отличия не объявляют о себе:

| | ноутбук | сервер |
|---|---|---|
| Postgres | опубликован на 5433 | не опубликован вовсе |
| API | опубликован на 8082 | не опубликован; доступен через web |
| web | `vite preview` — дев-сервер | Caddy отдаёт собранный бандл |
| секрет сессии | принимается отладочный | слабый секрет останавливает запуск |
| демо-набор | можно включить | невозможен: `SEED_MODE` пуст |
| пропущенная переменная | молча подставится умолчание | compose не стартует и называет её |

## Установка, по шагам

### 1. Код на сервере

```bash
ssh root@204.168.149.105
git clone https://github.com/mkodzya/ev8-ops.git /srv/ev8-ops && cd /srv/ev8-ops
```

### 2. Вход

```bash
docker compose -p ev8-edge -f docker-compose.edge.yml up -d
```

Проверка: `curl -I http://ops.ev8.ge` отвечает перенаправлением на https. Если
нет — A-запись ещё не разошлась; сначала DNS, потом всё остальное.

Через тот же вход отдаются макеты нового сайта ev8.ge:
`https://test.ops.ev8.ge/garage/` — статичные страницы из
`/srv/ev8-site-preview/www/` на сервере, вне этого репозитория (Mika,
01.10.2026). Вход по логину `ev8`; пароль задаёт Mika:

```bash
ssh -t root@204.168.149.105 /srv/ev8-ops/deploy/set-site-password.sh
```

`--lock` ставит пароль, которого никто не знает. Перезапуск входа
(`docker compose -p ev8-edge -f docker-compose.edge.yml up -d`) на несколько
секунд закрывает и прод — только по слову Mika.

### 3. Тестовый стенд (`develop`)

```bash
cp .env.prod.example .env.test     # WEB_PORT=5174, свои секреты
docker compose -p ev8-test --env-file .env.test -f docker-compose.prod.yml up -d --build
```

### 4. Прод (тег)

```bash
git fetch --tags && git checkout 1.0.0
cp .env.prod.example .env.prod
docker compose -p ev8-prod --env-file .env.prod -f docker-compose.prod.yml up -d --build
```

Первый запуск сам накатит миграции и заведёт владельца из `OWNER_EMAIL` и
`OWNER_PASSWORD` — только на пустой базе. Проверка:
`https://ops.ev8.ge/api/health` → `{"ok":true}`.

Прод собирается только по тегу на `main` (`practices.md` §2). Пока это правило
держит человек.

### 5. Копии

```bash
crontab -e
# каждый день в 04:10 по Тбилиси
10 4 * * * cd /srv/ev8-ops && BACKUP_DIR=/srv/ev8-backups deploy/backup.sh ev8-prod >> /var/log/ev8-backup.log 2>&1
```

`backup.sh` не просто снимает дамп: он восстанавливает его в одноразовую базу и
считает строки. Файл, который не восстановился, копией не считается и роняет
задание с ошибкой в лог.

**Раз в месяц руками:** свежий дамп на внешний диск, вне сервера и вне облака,
которое синхронизируется само. В дампе живые имена, телефоны и личные номера.

### 6. Тест и прод — как в Self Platform

Порядок работы тот же, что в Self Platform (решение Mika, 28.09.2026). В
`develop` вливают двое (Mika и Kardu); **после слияния сессия Mika сразу
выкатывает `develop` на test.ops.ev8.ge**:

```bash

```

Скрипт подтягивает `develop` и пересобирает стек `ev8-test` с `nice`, если
то, что работает на стенде, отстаёт (последняя удачная сборка записана в
`/srv/ev8-test.deployed`). Сборка упала — стенд остаётся на прежнем, в ответе
хвост лога. Две сборки разом не пойдут: скрипт держит замок. Прод не трогает.
Без `--now` скрипт ничего не делает; строку cron, оставшуюся с нескольких
часов автообновления 28.09, `--now` убирает сам.

Что было — `tail /var/log/ev8-follow.log`: строка на каждую выкатку, с
коммитом, на котором теперь стенд.

**Прод — только по слову Mika.** До 12.10.2026 релиз выпускала сессия Mika
(ветка `release/X.Y.Z`, версии, `main` с аннотированным тегом, обратно в
`develop`) и выкатывала его:

```bash
ssh root@204.168.149.105 /srv/ev8-ops/deploy/deploy-prod.sh X.Y.Z
```

**С 12.10.2026 всё это — одна команда, и запускает её Mika** на своём Mac, в
основной папке проекта (`deploy/release.sh`; в тот день система разрешений
сессии отказала ей в шагах релиза):

```bash
~/Desktop/claude-mika/ev8-ops-platform/deploy/release.sh X.Y.Z "что в релизе"
```

Она проверяет, что `develop` чист и совпадает с GitHub, ставит версию в пять
`package.json`, сливает релиз в `main` с аннотированным тегом (`main` и тег
уходят одной отправкой — оба или ни одного), вливает релиз обратно в
`develop`, запускает на сервере строку выше и обновляет тестовый стенд.
Запущенная ещё раз после сбоя, идёт с первого несделанного шага.
`--no-deploy` первым словом — собрать и отправить релиз без выкладки.

`deploy/deploy-prod.sh` берёт только тег, который есть на `main`. Сначала
снимает копию прод-базы с той же проверкой восстановления, что и ночная;
копия не восстановилась — релиз не идёт, прод не тронут. Потом переключает
`/srv/ev8-prod` на тег и пересобирает стек `ev8-prod`. Сборка упала — в
ответе хвост лога и команда отката на прежний тег. Журнал релизов —
`/var/log/ev8-release.log`. Скрипт лежит в тестовой копии (`/srv/ev8-ops`),
но работает только с `/srv/ev8-prod`.

5. Вход владельца работает; после первого входа сменить пароль в «Мой вход» и

6. `deploy/backup.sh ev8-prod` — прошёл и написал «restored».

## Забытый пароль

Пароль в базе не лежит: лежит односторонний слепок, из которого пароль не
восстанавливается. Забытый пароль поэтому не вспоминают, а заменяют:

```
/srv/set-password.sh ev8-prod .env.prod mika@selfstudio.se
```

Скрипт (`deploy/set-password.sh`, на сервере лежит копия в `/srv`) спрашивает
новый пароль дважды и не показывает его при наборе. Пароль уходит в контейнер
по стандартному вводу и возвращается уже слепком — в историю команд, в список
процессов и в логи он не попадает. Старые сессии на других устройствах после
смены закрываются, счётчик неудачных попыток обнуляется.

Стенды независимы: у `ev8-prod` и `ev8-test` свои базы, пароль меняется на
каждом отдельно (для теста — `ev8-test` и `.env.test`, из `/srv/ev8-ops`).

## Заявка с сайта на почту

Новый сайт (`mkodzya/ev8-site`) может отправлять заявку в очередь не в WhatsApp, а
письмом: `POST /api/site/queue` (имя, телефон, текст заявки) → письмо на ящик
компании. В базу и в логи заявка не пишется. Пока почта не настроена, адрес отвечает
503, и сайт должен оставить кнопку WhatsApp. Попросил Kardu 06.10.2026; решение —
п. 71 реестра книги.

На тестовом стенде включает Mika одной командой — скрипт спросит ящик и пароль приложения
(на экране он не виден), запишет настройки, перезапустит стенд и проверит, что ящик принял вход:

```
ssh -t root@204.168.149.105 /srv/ev8-ops/deploy/set-site-mail.sh
```

На боевом стенде — то же с `--prod` (перезапускается только API прода, несколько секунд). Без этого
заявки с ev8.ge никуда не приходят: WhatsApp с сайта убран 11.10.2026, запасного пути нет.

```
ssh -t root@204.168.149.105 /srv/ev8-ops/deploy/set-site-mail.sh --prod
```

Выключить: тот же скрипт с `--off`. То, что он записывает в `.env` стенда:

```
SITE_MAIL_HOST=…              # сервер исходящей почты ящика
SITE_MAIL_PORT=587            # 587 — STARTTLS. Не 465: с этого сервера 465 и 25 закрыты хостингом, соединение молчит
SITE_MAIL_USER=info@ev8.ge
SITE_MAIL_PASSWORD=…          # пароль приложения, не пароль ящика
SITE_MAIL_TO=                 # пусто — письмо уходит в тот же ящик
```

- **Пароль — только пароль приложения**, созданный для этого: он отзывается отдельно,
  не трогая пароль ящика, и не даёт войти в аккаунт через браузер. Но он **не ограничен
  отправкой**: с ним почтовая программа может и читать письма этого ящика. Поэтому лучше
  отдельный ящик только для отправки, а не общий ящик компании; пароль самого ящика на
  сервер не кладётся никогда.
- Ящик info@ev8.ge — Google (Mika, 07.10.2026): `smtp.gmail.com`, порт 587, пароль
  приложения — в настройках безопасности аккаунта (нужна двухэтапная проверка).
- После правки `.env` — перезапуск стенда обычным путём (`follow-develop.sh --now`
  для теста, `deploy-prod.sh` для прода).
- Проверка на тесте: заявка с предпросмотра сайта → письмо в ящике. Ответ 502 и
  строка `site queue mail not sent` в `docker compose logs api` — ящик не принял
  вход: неверный сервер, порт или пароль.
- Защита от спама: скрытое поле для ботов, не больше трёх заявок с одного телефона
  и тридцати всего за час. Счётчик в памяти и сбрасывается при перезапуске.
- Для боевого сайта на ev8.ge вход должен отправлять его `/api/site/*` на прод-стек
  (`edge/Caddyfile`) — сделано с запуском сайта 12.10.2026.

## Связь с Kommo

EV8 Ops раз в пять минут спрашивает Kommo, какие сделки стоят в этапе аренды, и
показывает владельцу, где это расходится с арендами здесь: строка «Расхождения с
Kommo» в «Сегодня» и список за ней. В Kommo ничего не пишется. Почему опрос, а не
вебхуки, и как устроено — `docs/adr/0012-the-kommo-link-polls.md`.

Пока токена нет, связь выключена целиком: ни строки, ни списка, ни запросов наружу.

С включённой связью удачная сделка ещё и **приходит сама** (`docs/adr/0015-…`): для сделки этапа
аренды и для выигранной сделки воронки продаж система находит карточку клиента по ссылке Kommo или
по телефону, а если её нет — заводит из контакта (имя, телефон, ссылка на сделку). В «Сегодня»
появляется строка «Оформить выдачу» или «Оформить продажу». Саму аренду и продажу оформляет человек.
Продажи, закрытые до первого опроса с этой версией, не приходят.

**Включить на тестовом стенде** — два действия, оба делает Mika.

1. Выпустить токен в Kommo (нужны права администратора): **Settings → Integrations →
   интеграция «EV8 Ops» → Keys and scopes → Generate long-lived token**, срок — самый
   длинный из предложенных. Kommo показывает токен один раз: скопировать.
   «Generate secret key» не нужен.
2. Положить его на стенд — скрипт спросит токен (на экране он не виден), запишет его,
   перезапустит стенд и сразу спросит Kommo:

```
ssh -t root@204.168.149.105 /srv/ev8-ops/deploy/set-kommo-token.sh
```

Ответ «Готово: Kommo принял токен. В этапе аренды сейчас сделок: N» — связь работает.
Выключить: тот же скрипт с `--off`.

**На боевой токен ставится последним, в день запуска.** С включённой связью боевой сам заводит
карточки по новым сделкам; такая карточка и та же, заведённая на тесте, — две разные строки с
одной сделкой, и `copy-static-to-prod.sh` откажется писать, пока они обе есть. Поэтому сначала
последний перенос статичного, потом аренды, потом токен.

**На боевом стенде** — тот же скрипт с `--prod`, и только после релиза, в котором связь
есть (1.3.0 и новее; на более старом скрипт скажет об этом и ничего не запишет). Токен
можно не выпускать заново и не вставлять: `--from-test` переносит строку с токеном из
`.env.test` в `.env.prod` прямо на сервере, на экран она не выводится.

```
ssh root@204.168.149.105 /srv/ev8-ops/deploy/set-kommo-token.sh --prod --from-test
```

Вставить другой токен — `ssh -t … set-kommo-token.sh --prod`; выключить — `--prod --off`.

То, что скрипт записывает в env-файл стенда:

```
KOMMO_TOKEN=…                 # долгосрочный токен приватной интеграции
# Нужны, только если что-то поменялось в Kommo; умолчания — в apps/api/src/lib/kommo.ts:
KOMMO_BASE_URL=               # https://ev8mopeds.kommo.com
KOMMO_RENTAL_PIPELINE_ID=     # воронка аренды «Gaqiraveba», 13427775
KOMMO_RENTED_STATUS_ID=       # этап «გაქირავებული», 103582579
KOMMO_SALES_PIPELINE_ID=      # воронка продаж «Gayidvebi», 11266343 (выигранные продажи приходят задачами)
KOMMO_CRON=                   # как часто спрашивать, по умолчанию */5 * * * *
```

- **Токен — секрет уровня администратора Kommo**, действует до пяти лет. Он лежит
  только в env-файле стенда (режим 600) и уходит в контейнер API переменной окружения.
  В чат, в коммит, в лог и в аргументы команд он не попадает; ответы Kommo в логи тоже
  не пишутся — в них имена. Утёкший токен отзывается там же, где выпущен: генерацией
  нового.
- Токен уходит только на `https://`-адрес: с `http://` в `KOMMO_BASE_URL` связь
  остаётся выключенной.
- **«Kommo не отвечает»** в «Сегодня» — Kommo молчит дольше двадцати минут: истёк или
  отозван токен, либо Kommo недоступен. Список при этом не пустеет: показано то, что
  Kommo ответил в последний раз, со временем. Причина одним словом — в логе:
  `docker compose -p ev8-test logs worker | grep -i kommo` (`unauthorized` — токен,
  `network` — связь, `rate_limited` — лимит запросов, `bad_answer` — Kommo ответил не
  тем, чего ждали).
- После правки `.env` руками — перезапуск стенда обычным путём (`follow-develop.sh --now`
  для теста, `deploy-prod.sh` для прода).

## Ключи Bank of Georgia (выписки по API)

Ключи выпускает компания сама в Business Online: `bonline.bog.ge/admin/api` → **Client
Credentials Flow** → имя `EV8 Ops`, пользователь интернет-банка (ключи получают его права —
нужен тот, у кого их меньше всего), **New IP address → Single IP address** `204.168.149.105`.
Банк показывает `client id` и `client secret`. Первые ключи выпущены 14.10.2026; книга, реестр, п. 8.

Положить их на стенд — скрипт спросит оба (secret на экране не виден) и счёт в лари, сначала
спросит банк с сервера (токен, затем курс НБГ через API) и запишет ключи, только если банк их
принял; потом перезапустит стенд и один раз попросит его прочитать операции дня:

```
ssh -t root@204.168.149.105 /srv/ev8-ops/deploy/set-bog-keys.sh
```

Ответ «Готово: стенд читает Bank of Georgia сам…» — всё работает. Дальше стенд спрашивает банк
сам (B11-03, `apps/api/src/lib/bog.ts`, ADR-0021): **каждые пять минут** — операции дня
(банк позволяет 800 таких запросов в сутки на счёт и валюту, пять минут — это 288), **раз в
ночь в 01:17** и при каждом запуске — полную выписку по вчерашний день, начиная с того, где
остановилась прошлая ночь. Строки ложатся в ту же очередь «Разобрать», что и из CSV, по тем же
правилам. Счёт можно не вписывать (Enter): скрипт возьмёт его из последней выписки Bank of
Georgia, загруженной на боевой, и покажет только последние четыре цифры. Номер счёта в
репозиторий не пишется. Если ключи уже лежат, а счёта нет (стенд пишет «не задан счёт»), — только счёт:

```
ssh -t root@204.168.149.105 /srv/ev8-ops/deploy/set-bog-keys.sh --account

## Перенос действующих аренд списком

Аренды, которые уже шли, когда начался EV8 Ops, переносятся не руками в мастере, а
списком (Mika, 08.10.2026). Загрузчик — `apps/api/src/loadRentals.ts`
(`lib/rentalLoader.ts`): каждую строку он заводит той же функцией, что и мастер выдачи
с галочкой «перенос действующей аренды» (`pickUp` с `transfer`), поэтому недели, залог,
события мопеда, парк и запись в журнале (`rental.transfer`) получаются такими же.

**Запускает Mika, со своего компьютера, две команды.** Сначала проверка — она ничего
не пишет:

```
ssh root@204.168.149.105 /srv/ev8-ops/deploy/load-rentals.sh < ~/Desktop/claude-mika/EV8-ops/rentals-to-load.json
```

Если в ответе «Список в порядке» — запись, та же команда с `--commit`:

```
ssh root@204.168.149.105 /srv/ev8-ops/deploy/load-rentals.sh --commit < ~/Desktop/claude-mika/EV8-ops/rentals-to-load.json
```

На тестовом стенде владельцев двое, поэтому там обе команды идут с `--owner e-mail`
сразу после `load-rentals.sh` (или после `--commit`) — см. ниже «Пишется от имени».

Сессия Claude этот скрипт не запускает — ни с `--commit`, ни без: она готовит список,
аренды на стенд переносит владелец.

- **Список лежит вне репозитория** (в нём сделки клиентов и адреса) и на сервере не
  сохраняется: он приходит по ssh на стандартный вход и уходит прямо в контейнер API.
  Ни файла, ни аргумента команды, ни строки в логе.
- **Клиент и мопед не вписываются, а находятся:** клиент — единственная карточка (не в
  архиве, не слитая), у которой в поле Kommo стоит эта сделка; мопед — по VIN.
- **Сначала проверяется весь список, потом пишется.** Одна проблема в любой строке — не
  пишется ни одна; строки пишутся одной транзакцией, так что и отказ посередине не
  оставляет половины. Проблемой считаются: нет карточки или их две; нет мопеда; мопед не
  «свободен» или стоит в парке продажи (перевод в аренду — решение владельца в мастере);
  дата выдачи не раньше сегодня; «оплачено по» — не последний день недели, считая от
  выдачи, или дальше текущей недели; получено залога больше залога; нет адреса ночной
  парковки; за клиентом числится долг; VIN или сделка в списке дважды; незнакомое или
  пропущенное поле; слово «Odoo» в заметке.
- **Повторный запуск безопасен.** Строка, чья аренда уже есть (тот же клиент, тот же
  мопед, не возвращена), пропускается с пометкой «уже есть» — список можно дополнять и
  запускать снова.
- **Отчёт** — по строке на аренду: метка, конец VIN, имя клиента, как оно записано на
  стенде, и одно из: «готова» с тем, что будет записано, номер аренды, «уже есть» или
  проблема словами. Телефонов, личных номеров и адресов в нём нет. «Неоплаченных недель
  на сегодня» — недели после «оплачено по», которые уже начались: с ними аренда придёт
  на стенд с долгом.
- **Пишется от имени владельца стенда.** Пока владелец на стенде один, называть его не
  нужно. Когда их станет несколько, загрузчик спросит, от чьего имени писать: к команде
  добавляется `--owner e-mail` (перед `<`). Не владельцу он отказывает. `OWNER_EMAIL` из
  `.env.test` для этого не годится: он нужен только для первой учётки в пустой базе, и
  на тестовом стенде в нём заглушка.
- **Боевой стенд называется вслух — `--prod`** сразу после `load-rentals.sh`; без него
  скрипт работает с тестовым. Перед записью на боевой снимается копия его базы с
  проверкой восстановления (как перед релизом); копия не восстановилась — ничего не
  пишется. На боевом должен стоять релиз с загрузчиком (1.3.0 и новее), иначе скрипт
  скажет об этом и остановится. На прод аренды переносятся по слову Mika.

```
ssh root@204.168.149.105 /srv/ev8-ops/deploy/load-rentals.sh --prod --owner mika@selfstudio.se < ~/Desktop/claude-mika/EV8-ops/rentals-to-load.json
```

Строка списка — запись с двенадцатью полями, все обязательны (где «не известно» —
`null`, а не пропуск); деньги в тетри, даты `ГГГГ-ММ-ДД`. Значения в примере выдуманы:

```
[
  {

    "weeklyRateTetri": 15000,

До запуска на боевой стенд переносится то, что не меняется изо дня в день (Mika,
08.10.2026): **модели, точки и карточки** — клиенты и поставщики. Источник — тестовый

```

Запись — та же команда с `--commit`. На боевом владельцев двое, поэтому к обеим
командам добавляется `--owner e-mail` — от чьего имени писать; без него скрипт спросит и
ничего не сделает. Сессия Claude этот скрипт не запускает.

Первый перенос — 08.10.2026: 11 моделей, одна точка, 25 карточек.

- **Мопеды — только по слову `--mopeds`.** Тогда приходит и список парка, но каждый
  мопед — «свободен», со своим парком и точкой и без аренды: кто на каком ездит,
  придёт вместе с арендами (`load-rentals.sh --prod`). Без этого слова мопеды не

  журнал, файлы в карточках клиентов, учётки людей, карточки из архива и слитые с
  другими.
- **Строка остаётся собой:** у неё тот же внутренний номер на обоих стендах, поэтому
  повторный запуск находит уже перенесённое. Пока на боевом нет аренд, он догоняет тест:
  что поменялось на тесте, обновится и там. Как только аренды появились — на боевом
  работают, и то, что там уже есть, не меняется: добавляется только новое.
- **Сначала проверяется всё, потом пишется.** Проблема — когда на боевом такая же
  строка уже заведена отдельно (та же модель, точка с тем же названием, карточка с тем
  же личным номером или сделкой Kommo, мопед с тем же VIN). Одна проблема — не пишется
  ничего; пишется всё одной транзакцией.
- **Данные нигде не сохраняются:** из контейнера тестового стенда они идут в контейнер
  боевого по трубе на сервере — ни файла, ни аргумента, ни лога. В отчёте только числа;
  имя появляется лишь у строки с проблемой, телефонов и личных номеров нет.
- **Перед записью — копия боевой базы** с проверкой восстановления, как перед релизом.
- **Оба стенда должны стоять на релизе, который знает эту команду** (1.3.0 и новее);
  иначе скрипт скажет об этом и остановится.

Решение: новый сайт (`mkodzya/ev8-site`) заменяет WordPress на ev8.ge; править его — через git

автоматическая: слияние в `develop` → https://test.ops.ev8.ge/garage/site/, слияние в `main` →
https://ev8.ge. Слияние в `main` сайта и есть его выпуск; выпускает Kardu, когда решит, или Mika
(Mika, 11.10.2026: «Карду может выпустить сайт когда захочет»). `main` здесь, в EV8 Ops, сервер,
и секреты — по-прежнему только Mika. DNS ev8.ge переключает Kardu (Mika, 11.10.2026: «пускай он
всё сам делает; единственное ему нельзя менять ERP»).

```
 GitHub Actions (ev8-site)          сервер 204.168.149.105
 ─────────────────────────          ───────────────────────────────────────────
 npm ci && npm run build ──tar.gz──▶ ssh ev8site@… test|prod
                                      └ /usr/local/bin/ev8-site-receive (deploy/site-receive.sh)
                                        /srv/ev8-site/<test|prod>/releases/<время UTC>
                                        /srv/ev8-site/<test|prod>/current → последний релиз
 Caddy (edge): ev8.ge → prod/current · test.ops.ev8.ge/garage/site/ → test/current
```

Ключ, который хранит GitHub, умеет одно: отдать архив сайта в `test` или `prod`, откатить
(`rollback prod`), показать `status`. Ни оболочки, ни других папок. Сборка идёт на GitHub, сервер
(3,8 ГБ) её не тянет. Релиз включается одной подменой ссылки — посетитель видит либо старый сайт,
либо новый. Хранятся пять последних.

Сценарий выкладки лежит в репозитории сайта (`.github/workflows/deploy.yml`), копии здесь нет. Кроме
выкладки по слиянию он раз в день, в 09:30 по Тбилиси, собирает обе ветки заново ради одной цифры —
цены бензина в калькуляторе (сайт читает её сам при сборке; в EV8 Ops этого нет — Mika, 11.10.2026).
Поэтому «пять последних» на проде — это обычно пять последних дней одного и того же кода: откат
`rollback prod` возвращает вчерашнюю сборку, а прежнюю версию сайта возвращают через git.

### Вход для ev8.ge: что чьё (с 12.10.2026)

Настройки входа лежат в папке `edge/`: `edge/Caddyfile` и `edge/entry.sh`. Папка подключена в
контейнер целиком, поэтому правка с нашей стороны применяется мягко, без пересоздания входа:
`docker exec ev8-edge-edge-1 caddy reload --config /etc/caddy/Caddyfile`. Старый `Caddyfile.edge`
в корне остаётся только до первого пересоздания входа с новым `docker-compose.edge.yml`, потом удаляется.

**Наше, в `edge/Caddyfile`** — то, что охраняет EV8 Ops, и общая механика:
- `/api/site/*` → прод EV8 Ops (заявка с сайта). Остальной API и всё `wp-*` — 410.
- Сертификат при первом заходе (`on_demand`), сжатие, `www.ev8.ge` → `ev8.ge`, страница 404 сайта.

**Сайта, в его репозитории (`edge/site.caddy` в `mkodzya/ev8-site`)** — куда ведёт старый адрес и
сколько браузер хранит картинку. Mika, 11.10.2026: «по сайту все задачи он должен без меня делать»,
поэтому эти правки Kardu вносит сам, сервер трогать не нужно:
- каждый выпуск сайта везёт файл `/_edge/site.caddy`; вход раз в 15 секунд сверяет его со своей копией
  (`/data/site-edge/current`) и, если он изменился, сначала проверяет весь конфиг с ним
  (`caddy validate`), и только потом берёт и мягко перезагружается;
- файл с ошибкой вход не берёт: действуют прежние настройки, причина — в журнале входа
  (`docker logs ev8-edge-edge-1 | grep -A2 '^edge:'`), выпуск сайта на шаге проверки падает;
- вход всегда стартует со своей копии последних принятых настроек, а не с только что присланного
  файла: сайт не может помешать ops.ev8.ge подняться;
- выпуск без файла настроек ничего не меняет.

Что эти настройки могут: они вставляются внутрь блока `ev8.ge`, то есть правила пишутся для адресов
ev8.ge. Отдельной стены между блоками в Caddyfile нет — файл, написанный с умыслом, мог бы затронуть
и соседние адреса; от ошибки защищает проверка перед применением, от умысла — то, что писать в
репозиторий сайта могут двое, Mika и Kardu. Посетителю файлы `/_edge/*` не отдаются (404).

## Когда что-то не так

- **Сертификат не выдаётся** — DNS не указывает на эту машину, или 80-й порт
  занят кем-то ещё. Caddy должен быть единственным, кто слушает 80 и 443.
- **Стек не поднимается с `variable is not set`** — в `.env` пустая строка. Это
  защита, а не ошибка.
- **Изменения не видны** — `--build`: web отдаёт собранный бандл, без пересборки
  остаётся прежний.
- **Откат** — `git checkout <предыдущий тег>` и та же команда запуска. История
  прода — список тегов.

ssh root@204.168.149.105 /srv/ev8-ops/deploy/set-names.sh --prod --owner mika@selfstudio.se --commit < ~/Desktop/claude-mika/EV8-ops/customer-names.json
```

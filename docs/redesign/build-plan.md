# План сборки редизайна EV8 Ops

Дата: 17.09.2026. Разработчик ([`docs/agents/developer.md`](../agents/developer.md)). Основание — утверждённая
схема [`blueprint.md`](blueprint.md) и прототипы `prototypes/`. Статус: **на утверждение Mika**.

Код на момент плана: `develop` @ e0ba87a — фронтенд 20 экранов (≈ 6 000 строк TSX), один `app.css` (1 352
строки), словари по ≈ 880 строк; API — Fastify и Prisma, 19 файлов роутов, 25 моделей, SQL-миграции своим
раннером; тесты — shared 87, api 149; у фронтенда тестов нет.

## 1. Главные решения сборки

Решения, которые меняют устройство продукта. Каждое — на утверждение вместе с планом.

| # | Решение | Почему | Альтернатива, от которой отказываюсь |
|---|---|---|---|
| Р1 | **Пересборка на месте, а не новое приложение.** Тот же стек (React 18, Vite, react-router 7, Fastify, Prisma, Postgres), те же стенды. Волна переписывает свои экраны, старые экраны волны удаляются в ней же | API и правила (периоды, деньги, себестоимость, PDF) верны и покрыты тестами — их не трогаем без причины. Две версии экрана одновременно не живут | Новый фронтенд рядом со старым — два продукта на месяц, двойная проверка |
| Р2 | **Дизайн-система — папка `apps/web/src/ds/`**: компоненты §3.5 схемы со всеми шестью состояниями, свой CSS у каждого компонента, токены — только `packages/shared/tokens.json`. Компонент появляется в той волне, где он впервые нужен; волна 1 закладывает основу | Один источник вида; guard уже ловит цвет литералом | CSS-фреймворк или библиотека компонентов — чужой визуальный язык и вес на телефоне |
| Р3 | **Страница `/design` — живой каталог `ds/`**: каждый компонент во всех состояниях, RU и KA, телефон и ноутбук. Тестировщик сверяет с `01-system.html` | Расхождение с прототипом видно на одном экране, а не в двадцати | — |
| Р4 | **Данные — TanStack Query** (одна зависимость, MIT): кэш по ключу, повтор, «данные на HH:MM» при потере связи, обновление после записи. Заменяет `useLoad` и ручные `api.get` в экранах | Состояния «загрузка / ошибка / нет связи / старые данные» (§3.2) — это ровно то, что эта библиотека делает; своя замена — месяц мелких ошибок | Свой кэш на `useState` — так сейчас, отсюда вечные «Загрузка» (QA-1-02) |
| Р5 | **Каждая запись — операция с ключом.** Форма получает ключ при открытии; API хранит ответ по ключу в таблице `operation_keys` и на повтор возвращает тот же ответ. Кнопка отправки — четыре вида §3.2 | B2-01: повтор после сбоя и двойной тап не создают вторую аренду, платёж, роль (QA-1-03) | Блокировать кнопку на клиенте — не спасает от обрыва связи после записи |
| Р6 | **Нет связи — минимум §3.2 в волне 1, очередь отправки — позже по факту.** Волна 1: черновик на устройстве (`ev8-draft:*`) у каждой формы и мастера, полоса «нет связи», «Повторить» после появления связи — безопасно благодаря ключу (Р5). Очередь отправки в фоне — отдельным решением после волны 3, если на приёмке Kardu будет терять связь при выдаче | Очередь с конфликтами («мопед уже выдан другим») — сложная и нужна не везде; ключ и черновик закрывают потерю и дубли уже сейчас | Очередь сразу — волна 1 растёт вдвое, не зная, нужна ли |
| Р7 | **Две роли в базе.** Миграция: `director` → `owner`, `mechanic` и `accountant` → `manager` (на стенде таких нет, кроме демо-директора), тип `user_role` пересоздаётся с двумя значениями. Права пересобираются под таблицу §2.1: у менеджера нет себестоимости, закупок, отчётов, сумм залогов на руках, выписок; API **режет поля** (себестоимость) в ответах, а не только прячет разделы | Решение Mika; сейчас все списки открыты правом `fleet.view` любой роли | Прятать только в интерфейсе — данные всё равно уходят в браузер |
| Р8 | **Адреса по новой структуре** (§2.1): `/money/…`, `/fleet/models`, `/service/stock`, `/reports/…`, `/settings/…`; старые адреса перенаправляются — закладки Kardu не ломаются | Вкладки раздела живут в адресе (§2.2) | — |
| Р9 | **Значки — `lucide-react`** (ISC), только нужные, по одному импорту | Схема §3.3; вес — по значку, не набором | Свои SVG — долго и неровно |
| Р10 | **Тесты фронтенда — Vitest для логики** (`web/src/lib`: ключи операций, черновики, форматирование, правила очереди «Сегодня», права на экране). Правила бизнеса — как сейчас, в `shared` и API. Браузерные e2e (Playwright) **не вводим**: на 8 ГБ это тяжёлая задача на каждый прогон; сценарии проходит тестировщик | Ловим то, что ломается молча; не держим машину занятой | e2e на каждую волну |
| Р11 | **B3-01 до первой записи команды:** `tools/migrate_stage1.py` отказывается писать в базу, где есть записи, созданные людьми после переноса (журнал `audit_log`), — без явного флага; умолчание Q1 | Повторный перенос не должен стереть работу | — |

## 2. Устройство фронтенда после волны 1

```
apps/web/src/
  ds/                 компоненты §3.5, каждый: Component.tsx + component.css, все состояния
    shell/            AppHeader, TabBar, ActionSheet, Rail, AvatarMenu, SyncBar, SectionTabs
    search/           SearchOverlay
    list/             ListToolbar, ListCard, DataTable, RecordHeader, Timeline, pills
    form/             Field, Picker, PhoneInput, MoneyInput, DateField, ReasonField, SubmitButton
    layer/            Sheet (= Drawer на ноутбуке), ConfirmDialog, Toast, UndoBar
    state/            Empty, Skeleton, LoadFailed, NoAccess, OfflineNote
  data/               TanStack Query: клиент, ключи запросов, хуки по разделам (useRentals, …)
  lib/                operation keys, drafts, format, nav rules (из shared), today queue rules
  sections/           экраны по разделам схемы: today/, rentals/, fleet/, service/, money/,
                      sales/, purchases/, reports/, settings/, customers/, profile/
  i18n/               словари (ka/ru/en) — разделы словаря по разделам продукта
  styles/             tokens.css (генерируется), base.css (сброс, типографика); app.css уходит по волнам
```

- **Оболочка** (волна 1) одна для всех экранов, включая ещё не переписанные: старые экраны получают новую
  шапку, панель, поиск и состояния сразу, свой вид — в своей волне.
- **Словари** остаются тремя файлами с формой из `en.ts`; guard i18n и errors-guard работают как сейчас.
- **Ширины** — токены `bpTablet` 720 и `bpLaptop` 900, в CSS через сгенерированные custom media, без чисел.

## 6. Риски

| Риск | Что делаю |
|---|---|
| Волны идут месяц, старые экраны живут рядом с новыми | Волна 1 даёт всем экранам новую оболочку, состояния и списки — разница остаётся внутри карточек и форм, а не в навигации |

| Миграция ролей на рабочем стенде | Миграция обратимая в пределах волны: старые значения пишутся в журнал; учётка Kardu заводится владельцем после миграции |

| Очередь отправки без связи понадобится раньше | Р6: решение после волны 3 по опыту приёмки; ключ операции уже сделает повтор безопасным |

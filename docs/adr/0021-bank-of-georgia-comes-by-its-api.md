# 0021. Bank of Georgia приходит по API: операции дня каждые пять минут, полная выписка раз в ночь

Дата: 14.10.2026. Статус: принято. Слово владельца — Mika 14.10.2026 (книга, `knowledge.md`, реестр, п. 8):
забирать операции дня раз в 5 минут и раз в сутки ночью сверяться с полной выпиской за вчера, «чтобы ничего не
потерять». Задача B11-03 ТЗ v2: выписки BOG по API, сверка с внесёнными (B2-03) обязательна. Дополняет
[ADR-0004](0004-matching-payments-by-rules-over-kept-lines.md) и
[ADR-0018](0018-a-bank-line-older-than-the-carry-over-waits-for-a-person.md); ничего в них не отменяет.

## Контекст

До сих пор выписки обоих банков приходили файлами: владелец выгружал CSV и загружал его на экране
«Деньги → Выписки». Перевод клиента попадал в систему через дни после зачисления, а между загрузками
система показывала ложную просрочку.

14.10.2026 Mika выпустил ключи Business Online API (Client Credentials Flow, вход только с адреса сервера
204.168.149.105) и положил их на тестовый стенд. У банка два нужных метода: операции текущего дня
(`api/v2/documents/todayactivities/{счёт}/{валюта}`, до 800 запросов в сутки на счёт и валюту) и выписка за
период (`api/v2/statement/{счёт}/{валюта}/{с}/{по}`, страницами по 1000 записей). Общий предел — 5 запросов в
секунду, сверх него 429 с `Retry-After`.

Одна операция может прийти тремя путями: файлом, пуллом дня и ночной выпиской. Каждый путь узнаёт свои
строки по-своему: файл — по хэшу текста строки, пулл дня — по id операции банка, выписка — по id проводки.
Эти ключи между собой не встречаются. Общее у них — сама операция: день, направление, сумма и номер
документа банка (в CSV — столбец «sabuTis #»).

## Решение

1. **Каждые пять минут стенд спрашивает операции дня** (`syncBogToday`, `apps/api/src/lib/bog.ts`; worker,
   `BOG_CRON`, по умолчанию `*/5 * * * *` — 288 запросов из 800). **Раз в ночь, в 01:17, и при каждом
   запуске worker** — полную выписку от дня, где остановилась прошлая ночь, по вчерашний
   (`reconcileBogNight`, `BOG_NIGHT_CRON`). Если ночь уже прочитана, ночное задание банк не спрашивает.
   Первая ночь начинается с последнего дня, который покрыл загруженный файл: дни между последним файлом и
   первым пуллом читаются тоже. Назад — не дальше 31 дня.
2. **Строки идут в ту же очередь и через те же правила, что и файл** (`ingest`,
   `apps/api/src/lib/statements/import.ts`): деньги, уже внесённые руками, связываются с платежом (B2-03),
   наличные, отвезённые в банк, — со взносом, строка с двумя признаками привязывается правилом, остальное
   ждёт человека в «Разобрать». Сумма без имени плательщика — тоже. Автор такой привязки — не человек
   (`actor = null`), в журнале — «Строки Bank of Georgia пришли сами» (`statement.pull`).
3. **Одна операция — одна строка** (`apps/api/src/lib/statements/sameLine.ts`). Строка уже есть, если есть
   строка с её ключом; иначе — если строка другого пути имеет то же направление, ту же сумму и тот же номер
   документа (ведущие нули не в счёт) в тот же день или на день раньше-позже; иначе — если у одной из двух
   номера нет, а день, направление и сумма совпадают. Каждая сохранённая строка покрывает одну входящую:
   три оплаты по 150 за день, две из которых уже есть, дают одну новую. Две строки одного пути одной не
   считаются никогда. При сомнении строка добавляется: дубль в очереди откладывается одним нажатием,
   потерянный платёж не видит никто.
4. **Работает в обе стороны.** CSV Bank of Georgia, загруженный после пулла, не задваивает строки, которые
   уже пришли по API, — и предпросмотр показывает их как «уже есть». У строк, загруженных из файлов раньше,
   номер документа восстановлен миграцией 0041 из сохранённого текста строки.
5. **День, который загруженный файл покрывает целиком, ночью не перечитывается.** Целиком — это каждый день
   периода файла, кроме последнего, и последний тоже, если файл загружен после того, как день кончился.
6. **На каждый счёт и день — одна выписка с именем «Business Online»** (`statements.source = 'api'`). Она
   заводится, когда день приносит первую новую строку, и пополняется в течение дня.
7. **Ключи — секрет сервера** (правило 3). Их кладёт Mika скриптом `deploy/set-bog-keys.sh`; код читает их из
   окружения и нигде не пишет — ни ключей, ни токена. Ответы банка содержат имена и счета, поэтому в лог
   идут только числа и наши слова для отказа (`unauthorized`, `forbidden`, `network`…). Без ключей связь
   выключена тихо: строки на экране нет, задания отвечают `off`.
8. **Только чтение.** Те же ключи могут создавать платёжные поручения (у них права пользователя
   интернет-банка). Код отправляет банку только запрос токена; к API — только `GET`.
9. **Счёт — в env-файле стенда** (`BOG_ACCOUNT`), не в репозитории. Пусто — стенд спрашивает о счёте из
   последней загруженной выписки Bank of Georgia: это слова самого банка. Валюта — лари, как и для TBC.

## Последствия

- Перевод в Bank of Georgia появляется в «Разобрать» через несколько минут после зачисления; если плательщик
  узнан и сумма сходится с долгом — сам привязывается к аренде.
- **Порядок поменялся.** Раньше выписка приходила после того, как менеджер вносил оплату руками, и правило
  B2-03 связывало строку с этой оплатой. Теперь строка приходит первой: если её привяжет правило, а потом
  менеджер внесёт ту же оплату переводом руками, деньги запишутся дважды. Вносить руками переводы в Bank of
  Georgia больше не нужно; защиты от этого в форме оплаты пока нет — отдельная задача.
- Карточные оплаты и суммы без имени по-прежнему ждут человека — API даёт то же, что файл.
- **Не проверено на живом банке:** форма ответа взята из документации банка (api.bog.ge), а не из
  настоящего ответа — с ноутбука API недоступен. Совпадение номера документа API и столбца «sabuTis #» файла —
  предположение по документации; если оно неверно, на стыке файла и API строки задвоятся (не потеряются).
  Первая ночь на стенде, начавшаяся с дня последнего файла, это покажет.
- TBC по-прежнему файлом; его API (Business Integration Services) — отдельный шаг.

## Уточнение 15.10.2026

Первые часы на тестовом стенде: шлюз банка отвечает 503 через раз (08:06 — 503, 08:10 — ответ, 08:15 — 503).
Поэтому:
- ответ 502, 503 или 504 — и на запрос токена, и на запрос к API — переспрашивается один раз через 3 секунды;
- в отказе названо, на каком шаге он случился — токен или API (`stage`); это наше слово, как и причина;
- ночное задание спрашивается **каждый час** (`BOG_NIGHT_CRON`, по умолчанию `17 * * * *`), а не только в
  01:17: пока вчерашний день прочитан, оно банк не спрашивает, а ночь, когда банк или стенд не ответил,
  догоняется в течение часа, а не через сутки.
- **Запасной путь для операций дня.** К 08:25 15.10 список операций дня (`todayactivities`) отвечал 503 на
  каждый опрос, кроме одного, а полная выписка (`statement`) — сразу. Если список дня отвечает 5xx, тот же
  пятиминутный опрос берёт сегодняшний день из выписки (`statement/{счёт}/GEL/{сегодня}/{сегодня}`). Строки
  получают ключи выписки (`api:entry:…`), поэтому ночное чтение узнаёт их по ключу. Отказ 4xx — не занятый
  шлюз, он называется, и выписку вместо него не спрашивают. Сколько раз в сутки выписку можно спрашивать,
  банк не пишет; 800 названы только для списка дня.

## Уточнение 16.10.2026: поздние проводки

Mika прислал из Business Online перевод 140 ₾ от 15.10, которого нет в EV8 Ops. В выписке банка за 15.10 он есть
(и комиссия 10 ₾), но номера проводок у обоих — около полуночи и позже: банк провёл их после 00:17, когда стенды
прочитали 15.10, а список операций 16.10 их не показывает — дата у них вчерашняя. Следующее чтение 15.10 было бы
только через сутки.

Теперь вчерашний день считается прочитанным, только если его прочитали **в 06:00 по Тбилиси или позже**
(`readAgain`, `MORNING_HOUR` в `apps/api/src/lib/bog.ts`): ночью в 00:17 день читается, в 06:17 — ещё раз, и что
банк провёл после полуночи, приходит к утру. Неудачное чтение прочитанным не считается. Лишний запрос к выписке —
один в сутки.

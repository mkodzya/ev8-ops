# Долларовые счета Bank of Georgia и TBC по API — план

Дата: 29.10.2026. Ветка `feature/usd-accounts`. Статус: **этапы 0–4 сделаны** в ветке 29.10.2026 (ADR-0051); этап 5
ждёт решений D2 и D3, этап 6 — первого живого обмена.

## Что известно

- У компании открыты два новых счёта в долларах: один в Bank of Georgia, один в TBC (Mika, 29.10.2026).
  Тот же это номер, что у счёта в лари (валюта на том же IBAN), или другой — неизвестно; план работает в
  обоих случаях. Номера в репозиторий не пишутся: их вписывает Mika скриптом на сервере.
- До этой ветки EV8 Ops читает по API по одному счёту в лари в каждом банке (ADR-0021, ADR-0026). Список
  счетов в `BOG_ACCOUNT` / `TBC_ACCOUNT` уже принимается, но валюта зашита как GEL: долларовый счёт был бы
  прочитан как лари.

## Решения владельца

- **D1 — А** (Mika, 29.10.2026): операции долларовых счетов читаются, хранятся и показываются отдельным
  блоком на «Деньги → Выписки», без разбора и вне итогов в ₾. Разбор (этап 5) — отдельно, позже.
- **D2** (откуда цифра в ₾ при разборе) и **D3** (ответы для займа) — открыты, нужны только для этапа 5.

## Поправки к плану ниже

- В миграции **нет защитного RAISE**: она должна проходить на любых данных. `migrate.mjs` запускается при
  старте контейнера api, и упавшая миграция уронила бы API на боевом. Отсутствие загруженного файла BOG не в
  лари проверяется только чтением перед релизом. Миграция идемпотентна (`IF NOT EXISTS`).
- Разрешённые валюты в коде — GEL, USD, EUR; скрипт по Enter предлагает USD.

## Рекомендация: основа — «minimal» (парковка валютных строк), затем разбор владельцем из «people»

Сначала два новых счёта начинают читаться, хранятся отдельно и видны владельцу. Лари, аренда, долги, НДС и отчёты в ₾ не меняются. Разбор валютных строк делается отдельным этапом по решению владельца. Каждый этап можно мёржить сам по себе. Схема одна для BOG и TBC и для USD и EUR, и для случая «та же валюта на том же IBAN», и для случая «новый IBAN».

### 1. Модель данных (миграция 0073; последняя сейчас 0072_todo_files.sql, ADR — 0050)
- `statements.currency` и `statement_lines.currency`: `text NOT NULL DEFAULT 'GEL' CHECK (~ '^[A-Z]{3}$')`. Список разрешённых валют (GEL/USD/EUR) проверяет код конфигурации, а не база.
- У валютной строки `amount_tetri` хранит минорные единицы её валюты (центы ×100, как сейчас считают tetri() bog.ts:300 и tbc.ts:357). Это пишется в комментарии к колонке и в schema.prisma.
- `statement_lines.bank_gel_tetri integer NULL`: эквивалент в лари, который даёт сам BOG (AmountBase / EntryAmount*Base). Только для справки, нигде не суммируется. У TBC он NULL. Нужен, чтобы позже решить про курс, ничего не перечитывая из банка.
- `statement_lines_resolution_check` пересоздаётся (как в 0070:12-14) с новым значением 'foreign'.
- CHECK `statement_lines_foreign_parked`: строка не в GEL всегда `status='ignored' AND resolution='foreign'`, строка в GEL никогда не 'foreign'. Строка сразу создаётся в этом состоянии, одним INSERT.
- Частичный индекс `(occurred_on) WHERE currency <> 'GEL'`.
- Таблица `bank_api_accounts (bank, account, currency, read_from, last_ok_at, last_try_at, last_failure, last_http_status, today_count, night_through, night_at, night_failure, night_http_status, night_mismatch_on, night_added, PK(bank, account, currency))`. Строка пары в лари заводится при первом чтении, её night_through берётся из bog_sync/tbc_sync. Сами bog_sync/tbc_sync продолжают писаться, но только по парам в GEL, поэтому нынешние карточки и «Сегодня» не меняются.
- Ключ строки. У строк в GEL ключ прежний. У валютных в ключ добавляется валюта: `api:today:USD:{Id}`, `api:entry:USD:{EntryId}`, `api:mv:USD:{movementId}`. UNIQUE(bank, natural_key) не трогаем (0005:47, schema.prisma:909). Так неважно, уникальны ли id банка между валютами одного IBAN.
- Выписка-день API ищется по (bank, 'api', account=IBAN, currency, day) вместо нынешнего поиска без валюты (apiDays.ts:134, 143). account остаётся голым IBAN, поэтому ownTransfers (ibanOf, ownTransfers.ts:28) не меняется.
- Защита миграции. Перед релизом проверяем только чтением, что на проде нет загруженного файла BOG со счётом не в GEL: тестовый стенд после copy-prod-to-test.sh, затем чтение прода в день релиза. RAISE в миграции оставляем последней линией. Помнить: migrate.mjs запускается при старте контейнера api (Dockerfile:21), а deploy-prod.sh:52-58 не откатывается сам. Если RAISE сработает, API на проде будет лежать.

### 2. Чтение из банка
- `BOG_ACCOUNT` и `TBC_ACCOUNT` — список «IBAN[CUR]», как BOG пишет счёт в файле. Без суффикса считается GEL, поэтому нынешний env работает. Суффикс только GEL/USD/EUR, иначе badAccount. Дубликаты убираются по паре, а не по IBAN (сейчас по IBAN: bog.ts:81, tbc.ts:82). Нужна новая функция `accountPairOf(raw, bankCode)` рядом с accountOf (apiDays.ts:42-47). Запасной путь «счёт последнего файла» (bog.ts:484-490, tbc.ts:452-458) остаётся только для GEL.
- Валюта пары идёт в URL BOG вместо константы (bog.ts:55, 257, 272, 281) и в AccountCurrencyCode TBC (tbc.ts:285, 307). TBC сравнивает currency операции с валютой пары, а не с 'GEL' (tbc.ts:351).
- Каждую пару читаем отдельно. Сейчас любой не-5xx на любом счёте отменяет весь пулл, включая лари (bog.ts:511, 517-521; tbc.ts:469-483), а ночь стоит на первом сбое (bog.ts:576; tbc.ts:539-543). Нужно, чтобы сбой пары писал статус этой пары, а строки остальных сохранялись. Ночной указатель и сверка TBC ведутся по паре.
- Новая пара один раз читает назад до 31 дня (NIGHT_MAX_DAYS, bog.ts:57). У BOG это один запрос выписки, у TBC около 32. Файлы закрывают дни только своей пары. Файлов не в GEL пока нет: BOG такой файл отклоняет, TBC такие строки пропускает (parse.ts:273).
- В outcome добавляется `accounts[]` вида {last4, currency, listed, added, failure}. Лог worker пишет строку по каждой паре, не больше 4 последних цифр (apps/worker/src/index.ts:178-182).
- Нагрузка (вывод из кода): каждая пара добавляет 288 запросов в сутки и 1–2 ночных. Токенов больше не становится (один на задание, bog.ts:479-481). Тестовый и боевой стенды читают одни и те же счета, так что на пару выходит около 576 запросов в сутки при лимите 800 по старой странице документации.

### 3. Очередь и правила
- `knownLines` (import.ts:62-76): currency добавляется в where обоих findMany, а не только в сравнение. Правило 2 по id TBC (sameLine.ts:136-145) не смотрит на сумму, поэтому фильтр должен стоять на выборке кандидатов.
- `ingest` (import.ts:179): строку не в GEL сразу записывает как ignored/foreign, без decideWithPayers, правил плательщиков и получателей. markOwnTransfers её не видит (берёт только unmatched, ownTransfers.ts:124).
- `daysInFiles` и `lastFileDay` сравнивают пару (apiDays.ts:91-119). Комментарий «one account at each bank» исправляется.
- Ручные пути. /restore (statements.ts:711) для валютной строки отвечает 409 foreign_line. В NOT_THERE добавляется 'foreign' (duplicates.ts:23). Счётчики «Отложено» явно фильтруют GEL.
- Файл BOG со счётом …USD/…EUR отклоняется понятной фразой. Это ParseError с отдельным кодом: сейчас все ParseError уходят как unreadable_statement (statements.ts:124, 135).

### 4. Экраны
- `formatMinor(minor, currency)` в packages/shared: для GEL вызывает formatGel, для остальных — fmtForeign, который переезжает из PurchasesPage.tsx:97-103.
- «Деньги → Выписки»: карточка на каждую пару («Bank of Georgia · USD»; «··NNNN» — только если в одном банке две пары одной валюты), у каждой свой статус. Ниже блок «Операции в валюте» только для чтения: строки за период, приход и расход по каждой валюте, подпись «не входит в итоги в ₾». Нужен новый `GET /api/statement-lines/foreign` с правом payments.reconcile.
- «Разобрать», «Сегодня», недельный отчёт, календарь, долги, экономика не меняются: валютная строка туда не попадает.
- i18n: новый `apps/web/src/i18n/bank-currency.ts` (En/Ru/Ka) и коды foreign_line и foreign_statement в errors.codes. Грузинский текст проверяет носитель.

### 5. Отчёты
- «Расходы» (expenses.ts:89-90) и «Поступления» (inbound.ts:201-202): `where currency='GEL'`. Без этого валютная строка попадает в apart.other (inbound.ts:247). Свежесть на «Выписках» (statements.ts:78) и на «Сегодня» (today.ts:154) тоже только по GEL. Итоги в ₾ не меняются.

### 6. Скрипты
- `--account` в этапе 0 показывает текущий счёт как «…NNNN», спрашивает «Заменить? да/нет» и отклоняет валютный суффикс. Сейчас он молча заменяет счёт в лари (set-bog-keys.sh:69-75, 157-158; set-tbc-keys.sh:164-165).
- `--add-account` в этапе 4 (идея из people и accounting). Скрипт показывает пары, по Enter берёт тот же IBAN, валюта выбирается 1/2. До записи пару проверяет банк изнутри контейнера через новый `POST /api/jobs/bank-probe` с токеном worker, наружу выходит только код ответа. Пара дописывается к списку одной строкой, стенд перезапускается, итог печатается по каждой паре. Проверочный запрос TBC берёт валюту пары, а не GEL (set-tbc-keys.sh:221). `--prod --from-test` переносит список.

### 7. Тесты (только выдуманные IBAN)
- Фальшивый банк BOG принимает валюту из URL (сейчас /GEL/ в bog.test.ts:64, 68). Случаи:
  - тот же IBAN в GEL и USD даёт две выписки-дня и две пары;
  - 403 на USD не мешает: строки GEL сохранены, статус GEL зелёный;
  - USD 150 не считается «уже есть» из-за GEL 150 ни по правилу 4, ни по id TBC;
  - ключи строк в GEL не меняются.
- tbc.test.ts: :158 остаётся (USD внутри GEL-пары даёт null), :211 берёт валюту пары.
- Новый тест: CHECK не даёт валютной строке стать unmatched; /restore отвечает 409; отчёты и свежесть её не считают; файл BOG …USD отклонён.
- Запускать по одному, с --runInBand и лимитом памяти.

### 8. Потом, по решениям владельца (этап 5, из people и accounting)
- Миграция снимает CHECK парковки и переводит валютные строки в unmatched. Строки уже лежат в базе, из банка ничего не перечитывается.
- В «Разобрать» появляется группа «В валюте», только для владельца (для не-владельца в where добавляется currency='GEL').
- Ответы: «Обмен валюты» (новая resolution fx_exchange, вне расходов и выручки); категория расхода в валюте строки; «Поставщику» с цифрой в ₾, которую вводит владелец, а подсказка берётся из последнего обмена или эквивалента банка; foreignMinor и foreignCurrency пишутся как есть (schema.prisma:802-803, money.ts:435-445); «Между счетами»; «Взнос учредителя»; «Прочий доход»; «Не наше».
- Защита на сервере: отказ foreign_line в claim() (import.ts:252) закрывает attach, split, link и goods paidNow (goods.ts:427). Плюс отказ в bank-deposit и deposit_payout.
- Валюта учитывается в decide, suggest, inBank, options, depositFor, expenseKey и в паре markOwnTransfers (одна валюта).
- В отчётах блок по валютам, итоги в ₾ только по GEL. Тест-инвариант: USD-строка не видна ни одной цифре в ₾.
- Этап 6, после первого живого обмена: подсказка «пара обмена» и приём валютных файлов BOG и TBC.

Валюта учитывается в decide, suggest, decideWithPayers, inBank, options, depositFor, expenseKey и в паре markOwnTransfers. Ответы: «Обмен валюты» (fx_exchange), расход в валюте строки, «Поставщику» с цифрой в ₾, между счетами, взнос учредителя, прочий доход, не наше. Ответы займа — по решению D3. Отчёты: итоги в ₾ только по GEL плюс блок по валютам. Интеграционный тест: USD-строку не видит ни одна цифра в ₾.

- Файлы: apps/api/migrations/0074_*.sql; apps/api/src/lib/statements/import.ts, reconcile.ts, payers.ts, expenses.ts, inBank.ts, options.ts, ownTransfers.ts; apps/api/src/routes/statements.ts, nav.ts, expenses.ts, inbound.ts; apps/web/src/pages/money/SortPage.tsx, IncomeAnswers.tsx, ExpenseAnswers.tsx; ExpensesReportPage.tsx, IncomingReportPage.tsx
- Готово, когда: Владелец разбирает валютную строку одним из разрешённых ответов. Менеджер не видит ни валютных строк, ни их числа. Попытка привязать валютную строку к аренде или товару отвечает 409. Оплата поставщику из USD даёт себестоимость по введённой цифре в ₾.

### Этап 6 — пара обмена и валютные файлы (после первого живого обмена)

## Что проверить по ходу

- Новые счета — это тот же IBAN с другой валютой или новые IBAN. Документация обоих банков намекает на тот же IBAN, но это вывод. Проверяет владелец в интернет-банке, ответ «тот же/другой». Дизайн работает в обоих случаях, ответ нужен, чтобы знать, что смотреть в тестах.
- Видят ли нынешние ключи новую пару и что банк отвечает, если прав нет или такой валюты у IBAN нет (пустой 200, 400 INVALID_ACCOUNT, 403 или 404). Проверка: probe в --add-account на тестовом стенде, только GET, наружу только код. Тестовый стенд ходит в банк с теми же ключами, прод не трогается.
- Какие поля на самом деле приходят в USD/EUR-ответе BOG: Credit/Debit/Amount/AmountBase в todayactivities; EntryAmountCredit/Debit, EntryAmount*Base, DocumentRate, DocumentSource/DestinationCurrency, EntryAccountNumber в statement. Проверка: на тестовом стенде одна запись в логе по паре со списком имён полей без значений. Живые ответы в валюте ещё никто не видел (ADR-0021:71-74), фикстуры придуманы (bog.test.ts:109).
- TBC: заполнено ли у USD-операций поле currency, какой знак у amount, есть ли exchangeRate и transactionType=5 у конвертации. Проверка: та же запись имён полей на тестовом стенде, плюс число операций по типам.
- Уникальны ли Id и EntryId у BOG и movementId у TBC между валютами одного IBAN. Префикс валюты в ключе делает этот вопрос безопасным. Проверка: на тестовом стенде посчитать, сколько id встретилось под двумя валютами (одно число).
- Лимиты BOG: 800 или 10 000 запросов в сутки на todayactivities (две официальные страницы расходятся) и 1 запрос выписки в минуту на счёт и валюту. Тестовый и боевой стенды опрашивают одни и те же счета одними ключами. Проверка: неделю смотреть на тестовом стенде, нет ли rate_limited в статусе пары. Особенно после старта worker, где пулл и ночь идут подряд (index.ts:283-284).
- Нет ли на проде загруженного файла BOG со счётом не в GEL: parseBog такой принял бы. Проверка: запрос на тестовом стенде после очередного copy-prod-to-test.sh, ответ одно число. В день релиза то же только чтением на проде, как требует порядок релиза.
- Как каждый банк записывает обмен GEL↔USD: один документ или два, одинаковый ли DocNo, кто стоит второй стороной, отдельная ли строка комиссии. Проверка: первый настоящий обмен на тестовом стенде, по полям без сумм. Нужно для этапа 6.
- Как выглядит CSV валютного счёта: у BOG суффикс в «angariSis #», kursi и eqv.lari; у TBC — Account Number и Currency. Проверка: один файл от владельца, читаются только заголовки, файл в репозиторий не попадает. Нужно для этапа 6.
- Не выводить в лог и не печатать номера счетов. В тестах, ADR и коммитах только выдуманные IBAN (репозиторий публичный).
